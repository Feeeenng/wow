# 第一版开发计划

## 1. 目标

第一版先完成一个可由两名团员真实使用的端云闭环：

1. 两台 Windows 设备登录并加入同一团队。
2. 客户端识别魔兽世界正式服、增量读取 CombatLog，并录制正确的游戏画面。
3. CombatLog 自动识别一次 Boss Pull 的开始和结束。
4. Pull 结束后约 5 秒内，Web 显示本场 Pull、成员视角和上传处理状态。
5. 客户端优先上传压缩原始日志，再可靠上传本场视频。
6. 云端汇总两份日志、生成基础事件时间线，并对齐两名成员录像。
7. Web 使用单播放器切换两名成员视角，切换后保持当前 Pull 时间。
8. 客户端、网络或 Worker 短暂中断后，任务可以恢复且不重复创建数据。

第一版不承诺 Pull 结束后 5 秒内视频可播放。视频可播放时间取决于录像大小、用户上行带宽和云端处理耗时。

## 2. 第一版范围

### 2.1 必须实现

- Windows 10、Windows 11，中国区正式服
- Tauri 2 + React/TypeScript WebView 客户端界面
- 简单账号登录、团队创建、团队加入和三种固定角色
- 平台用户、设备和游戏角色 GUID 的独立关联
- WoW 进程、游戏窗口和 CombatLog 路径检测
- Rust 后端通过 OBS Studio WebSocket 控制录制，编码器由 OBS Studio 配置并由客户端读取状态
- CombatLog 增量读取、不完整行缓冲、读取位置持久化
- `ENCOUNTER_START`、`ENCOUNTER_END`、参战角色、死亡和基础施法事件
- Pull 结束后上传完整原始日志区间和单场视频
- SQLite 持久上传队列、预签名直传、S3 Multipart、失败重试和断点恢复
- PostgreSQL 业务状态、MinIO 原始文件、Redis/Celery 异步处理
- FFmpeg/ffprobe 校验以及 HLS 播放产物
- 活动列表、Pull 状态、单播放器视角切换和基础事件时间线
- 两台真实 Windows 设备的端到端验收

### 2.2 暂不实现

- 战斗中视频上传或直播
- 二十人规模优化
- 多路视频同时播放
- 自适应多码率转码
- 完整 DPS/HPS 统计
- AI 自动复盘或自动判责
- 复杂 RBAC、实时批注和移动端
- WCL 导入、排轴、STT、NSRT
- 自动更新和完整商业化运维体系

## 3. 交付阶段

工作量按个人全职开发估算，不包含等待真实团本、代码签名和线上基础设施审批的时间。

| 阶段 | 目标 | 预计工作量 | 退出条件 |
| --- | --- | ---: | --- |
| M0 | 建立可启动的三端骨架 | 3–4 天 | 客户端、API、Worker、Web 和本地基础设施均可启动 |
| M1 | 验证 OBS 录制实现 | 7–10 天 | 能稳定得到一段包含开战前画面的单场录像 |
| M2 | 完成 CombatLog 与本地 Pull 状态 | 5–7 天 | 重启后继续增量读取，并正确识别一场 Pull |
| M3 | 完成账号、团队和上传入口 | 5–7 天 | 两个用户能加入同一团队并创建 Pull 上传会话 |
| M4 | 完成可靠日志与视频上传 | 5–7 天 | 断网和重启后可恢复，重复请求不产生重复文件 |
| M5 | 完成日志解析与双视角同步 | 7–10 天 | 两份日志合并为统一时间线，两路录像得到同步偏移 |
| M6 | 完成媒体处理与 Web 复盘 | 7–10 天 | Web 能播放并保持时间切换两名成员视角 |
| M7 | 完成可靠性验收和第一版收尾 | 5–7 天 | 完成第一版验收清单并记录实测指标 |

P0 技术闭环为 M0–M6，预计 39–55 个工作日。完成可靠性收尾的第一版为 M0–M7，预计 44–62 个工作日。

## 4. 分阶段任务

### M0：工程骨架

任务：

- 建立 `client/`、`backend/`、`web/`、`migrations/` 和 `docker/` 的最小目录结构。
- 建立 Tauri 2 + React/TypeScript 客户端外壳和 Rust command/event 边界。
- 建立 Rust command/event 边界，React 只通过稳定接口读取状态和发出操作。
- 建立 FastAPI 健康检查、Celery Worker 探活和 React 应用入口。
- 使用 Docker Compose 启动 PostgreSQL、Redis 和 MinIO。
- 建立统一配置模块、结构化日志和本地开发启动说明。

验证：

- Windows 上客户端可以启动，React 能通过 Tauri command 调用 Rust 健康检查。
- API、Worker、PostgreSQL、Redis 和 MinIO 健康检查正常。
- Web 可以调用 API 健康检查并显示结果。

### M1：录制技术验证

OBS 生态已经确定，最小接入方式已锁定为 Rust 后端使用 `obws` 连接 OBS Studio WebSocket。本阶段继续验证真实 OBS 环境，不实现独立 Recorder Host，也不让 React 直接连接 OBS。

任务：

- 检测 OBS Studio 进程、WebSocket 版本和鉴权状态，通过 Rust command/event 向 React 暴露结构化状态。
- 通过 OBS WebSocket 验证 WoW 窗口采集源、录制开始/停止、输出文件路径和回放缓冲控制。
- 读取 OBS 当前编码器、分辨率、帧率和码率配置，不由 React 伪造运行状态。
- 固定第一版基准参数：H.264、1080p、30 FPS、1 秒关键帧；质量值通过实测确定。
- 记录系统音频，麦克风默认关闭。
- 输出崩溃后可恢复的中间文件，并在 Pull 结束后生成单场视频。
- 实测黑屏、无边框、多显示器、窗口重建和编码器过载场景。

验证：

- CombatLog 事件延迟 20 秒到达时，成片仍包含真实开战画面。
- 连续完成 10 次开始、结束和重新进入缓冲，不丢失下一场 Pull。
- 录制 10 分钟后记录 CPU、GPU、内存、码率、文件大小和音画同步数据。
- OBS Studio 未启动、鉴权失败、连接中断或录制失败时，Rust 返回可定位错误且 Tauri 主进程继续运行。

### M2：CombatLog 与本地 Pull 状态

任务：

- 实现目录监听并以定时文件状态检查作为兜底。
- 使用 SQLite 保存文件标识、字节位置、不完整尾行和最后确认时间。
- 正确解析包含年份和小数秒的日志时间，不丢弃毫秒精度。
- 先实现 Encounter、参战角色、死亡和基础施法事件，不做完整统计分析。
- 建立本地 `activity_id`、`pull_id`、日志区间、角色 GUID 和录像文件关联。
- 客户端重启后恢复未结束 Pull 或将其标记为异常结束。

验证：

- 日志写入被切在任意字节位置时不产生半行事件。
- 文件轮转、日志截断、游戏重启和客户端重启后不重复或跳过已确认行。
- 使用真实中国区日志样本正确识别至少一次击杀和一次灭团。

### M3：账号、团队和上传入口

任务：

- 实现简单账号登录和短期访问令牌，不引入复杂 RBAC。
- 实现团队、成员、固定角色、设备和游戏角色绑定。
- 平台 `user_id` 作为数据归属，CombatLog 角色 GUID 作为游戏角色标识。
- 建立活动、Pull、成员录像、日志来源和上传对象基础表。
- 实现创建 Pull、登记文件、获取预签名上传地址和查询处理状态 API。
- 所有创建与确认接口使用客户端稳定 ID 保证幂等。

验证：

- 两个账号加入同一团队后可以登记各自视角。
- 非团队成员不能读取或上传该团队数据。
- 重复提交相同客户端 Pull 和文件 ID 只返回同一资源。

### M4：可靠上传

任务：

- Pull 结束后立即提交元数据，使 Web 尽早显示处理状态。
- 优先压缩并上传本场完整原始 CombatLog 区间。
- 小文件使用预签名 PUT，大视频使用 S3 Multipart。
- SQLite 持久化 upload ID、Part、ETag、校验值、重试次数和下一次重试时间。
- 实现有限并发、指数退避、上传限速、取消和服务端完成确认。
- 服务端保存文件最终状态，Redis 不作为上传状态的唯一来源。

验证：

- Pull 结束后约 5 秒内，Web 能看到 Pull 和上传状态。
- 上传过程中断网、关闭客户端并重新启动后，从未完成 Part 继续。
- 重复上传、乱序确认和重复完成 Multipart 不产生重复录像。
- 日志或单名成员视频失败不阻塞其他成员。

### M5：云端日志解析与同步

任务：

- 原始压缩日志保存到 MinIO，Celery 流式读取和解析。
- 根据团队、Encounter、难度、时间窗口和参战成员重合度关联同一 Pull。
- 为事件建立版本化指纹，合并重复事件并保留全部来源。
- 第一版统一事件流包含 Pull 边界、角色、死亡和基础施法。
- 分别保存日志时间、客户端单调时钟、录像时间和统一 Pull 时间的映射。
- 计算每名成员录像偏移和可信度，允许后续人工微调。

验证：

- 两份同场 CombatLog 不会把重复死亡和施法显示两次。
- 删除其中一份日志后，另一份仍能生成基础时间线。
- 两名成员录像跳转到同一事件时，实测偏差达到 P0 记录的可用阈值。
- 解析任务重复执行不会重复写入事件。

### M6：媒体处理与 Web 复盘

任务：

- 使用 ffprobe 校验编码、时长、时间戳、音轨和文件完整性。
- H.264/AAC 兼容输入走 FFmpeg stream copy，生成 CMAF/fMP4 HLS。
- 不兼容输入进入明确的失败状态；第一版不提前建设完整转码矩阵。
- Web 实现登录、团队切换、活动列表、Pull 列表和处理状态。
- 使用单个 `HTMLVideoElement` 和 HLS.js 播放当前成员视角。
- 切换成员时保持统一 Pull 时间、播放状态、倍速和音量。
- 展示死亡和基础施法时间线，点击事件跳转视频。

验证：

- 两个视角均能播放，切换后保持同一 Pull 时间。
- 上传中、处理失败、录像缺失和同步可信度不足均有明确状态。
- 页面不会同时下载全团所有视频内容。

### M7：端到端验收

任务：

- 使用两台真实 Windows 设备完成一次团本测试。
- 覆盖一台设备断网、客户端重启、Worker 重启和重复任务。
- 记录 Pull 状态可见时间、日志解析时间、视频上传时间、媒体处理时间和视角切换时间。
- 修复阻断闭环的问题，不在本阶段增加第二版功能。
- 补充部署、备份、日志脱敏和数据删除说明。

验证：

- 完成 `docs/PRODUCT.md` 第 14 章验收流程。
- 所有失败均能定位到用户、设备、Pull、文件和处理阶段。
- 实测结果写回产品验收阈值和配置默认值。

## 5. 最小数据模型

第一版优先建立以下业务实体，字段在实现前通过迁移设计确认：

- `users`：平台账号
- `teams`、`team_memberships`：团队与固定角色
- `devices`：客户端设备
- `characters`、`user_characters`：游戏角色 GUID 与平台用户历史关联
- `activities`、`pulls`：团本活动和统一 Pull
- `pull_sources`：每个客户端上报的本地 Pull 来源
- `log_files`、`video_files`：原始文件和上传状态
- `combat_events`、`event_sources`：统一事件与来源关系
- `video_assets`：原始录像和 HLS 产物
- `sync_mappings`：成员录像到统一 Pull 时间的映射
- `processing_runs`：解析和媒体处理的最终状态及错误

Redis 只承载 Celery Broker 和带 TTL 的缓存。用户可见状态、幂等键和处理结果必须保存到 PostgreSQL。

## 6. 开发顺序约束

- M1 录制 Spike 未通过前，不开发完整客户端设置页面。
- M2 的真实 CombatLog 样本未验证前，不扩展完整统计事件模型。
- M4 断点恢复未通过前，不进行二十人并发优化。
- M5 双视角同步未通过前，不开发复杂复盘分析功能。
- M6 单播放器切换未通过前，不增加预加载和缓存优化。
- 每个阶段只处理阻断下一阶段的缺陷，非核心需求进入后续清单。

## 7. 第一批实现任务

代码实现启动后，按以下顺序建立第一批任务：

1. 初始化仓库目录和本地基础设施。
2. 建立 Tauri Rust 健康检查和前端 command/event 适配。
3. 完成 OBS Studio WebSocket 连接、游戏窗口源检测和 30 秒录像 Spike。
4. 完成 NVENC、QSV、AMF、x264 枚举和基准测试。
5. 验证持续缓冲与滚动文件两种方案，记录结论并只保留选中方案。
6. 建立 CombatLog 增量读取器和不完整行测试样本。
7. 建立 SQLite 文件位置和本地 Pull 状态。
8. 用 `ENCOUNTER_START`、`ENCOUNTER_END` 驱动一次完整本地录像。
9. 输出本地 Pull manifest、压缩日志和单场视频。
10. 在进入账号、上传和 Web 开发前完成 M1、M2 技术评审。
