# 魔兽世界团队多视角云端复盘平台

## 1. 产品方向

本项目面向魔兽世界中国区正式服团队，建设由 Windows 客户端采集、云端处理、Web 端复盘的团队战斗记录平台。

核心能力是：

1. 客户端调用或封装 OBS 录制游戏画面。
2. 客户端持续读取魔兽世界 CombatLog，并识别活动、首领战和 Pull。
3. 视频与战斗日志在 Pull 结束后以可恢复方式上传云端。
4. 云端解析日志并将同一场战斗中不同团员的视频对齐到统一时间线。
5. 团队通过 Web 页面在成员之间切换第一视角录像，结合统一事件时间线完成复盘。

`reviewtool.gg` 作为产品体验参考，`aza547/wow-recorder` 作为客户端录制与日志关联技术路线参考。是否复用其代码、依赖或发布产物，必须在完成许可证、再分发条件、安全性和中国区客户端兼容性评估后决定。

## 2. 核心价值

平台需要解决三个问题：

- 团员无需手工剪辑和逐个上传录像，客户端自动完成采集、关联和上传。
- 团长无需手动寻找不同录像中的同一个时间点，云端自动同步全部可用视角。
- 复盘不再只看统计表，而是能从战斗事件直接跳转到对应玩家的现场画面。

“全部团员视角”指同一 Pull 下所有已安装客户端、已授权录制且成功上传的成员视角。平台必须明确展示缺失、上传中、处理失败或时间同步不足的视角，不能假定每名团员都有录像。

## 3. 第一阶段边界

### 3.1 支持范围

- 区域：中国区
- 游戏类型：正式服
- 客户端系统：Windows 10 和 Windows 11
- 默认语言：简体中文
- 使用场景：固定团队的团本训练、开荒和击杀复盘
- 采集内容：游戏画面、可选游戏音频、CombatLog 和必要的客户端诊断信息

### 3.2 第一阶段核心闭环

安装并登录客户端
→ 加入或绑定团队
→ 检查游戏、CombatLog 和录制状态
→ 进入团本后自动创建活动会话
→ 开始录制并持续读取日志
→ 识别每次 Pull
→ Pull 结束后上传本场视频和完整原始日志
→ 云端完成解析、转码与时间同步
→ Web 端打开活动和 Boss
→ 选择 Pull
→ 在统一时间线上查看和切换团员视角
→ 从死亡、施法或机制事件跳转到对应画面
→ 添加复盘标记和结论

### 3.3 第一阶段不作为核心

- WCL 不再是主要数据入口，可作为后续补充数据源。
- 团本排轴、STT 和 NSRT 导出不进入第一阶段核心闭环。
- 不建设完整公会管理、装备分析、招募、出勤或 Loot Council。
- 不提供直播或观众实时观看能力。

## 4. 用户与权限

### 4.1 用户角色

第一阶段使用三种简单角色：

#### 团长

- 创建和管理团队
- 邀请或移除成员
- 查看团队全部活动、日志和录像
- 管理复盘标记
- 设置团队数据保留策略
- 删除团队活动数据

#### 分析员

- 查看团队全部活动、日志和录像
- 创建和编辑复盘标记
- 标记重点 Pull 和关键事件

#### 团员

- 上传自己的录像和日志
- 查看所在团队授权范围内的复盘
- 管理自己客户端的录制、音频和上传设置
- 查看并删除自己尚未归档的本地缓存

第一阶段不建设复杂 RBAC。所有视频和日志访问必须先验证团队归属和当前用户权限。

### 4.2 团队信息

团队至少保存：

- 团队名称
- 公会名称，可选
- 中国区服务器
- 当前游戏版本
- 数据保留天数
- 默认录制与上传建议
- 创建者和创建时间

### 4.3 用户与游戏角色关联

平台身份和游戏角色身份必须分开处理：

- 登录后的平台 `user_id` 用于鉴权、团队归属、上传者审计和数据删除。
- CombatLog 中的角色 GUID 用于识别参战角色、关联同一角色的日志事件和第一视角录像。
- 每次上传同时携带平台用户、设备、游戏角色 GUID、角色名、服务器和客户端生成的 Pull 标识。
- 云端可以通过 CombatLog 自动发现和匹配角色，但不得把日志中的角色 GUID 当作登录凭证或上传授权。
- 同一平台用户可以绑定多个游戏角色；角色转服、改名或 GUID 变化时保留历史关联，不覆盖旧活动数据。

## 5. Windows 客户端

### 5.1 客户端职责

客户端只负责本地采集、轻量识别、可靠上传和状态反馈。复杂战斗分析、跨成员关联和复盘结果生成放在云端。

客户端需要：

- 用户登录和团队绑定
- 自动发现或手动选择魔兽世界安装目录
- 检查 CombatLog 是否启用
- 选择正确的 CombatLog 文件并持续读取新增内容
- 调用或封装 OBS 录制游戏窗口
- 监控游戏进程、录制状态、磁盘空间和网络状态
- 建立本地活动、Pull、完整日志区间和视频文件的关联
- 保存可恢复的上传队列
- 展示上传速度、剩余数量、失败原因和重试状态
- 在上传确认后按策略清理本地临时文件

### 5.2 录制设置

第一阶段至少支持：

- 选择游戏窗口或显示器采集源
- 录制分辨率
- 帧率
- 视频质量档位
- 是否录制游戏音频
- 是否录制麦克风，默认关闭
- 本地缓存目录
- 最大缓存空间
- 上传带宽限制
- 仅在战斗期间录制或整场活动录制

客户端必须提供录制预览或明确的采集状态，避免团本结束后才发现黑屏、错误窗口或无音频。

### 5.3 日志读取

客户端需要增量读取 CombatLog，不重复扫描整个文件。日志读取必须处理：

- 文件切换和日志轮转
- 游戏重启
- 客户端重启后的读取位置恢复
- 不完整行
- 编码和换行差异
- 重复事件
- 本地时间变化
- 断网期间的暂存与补传

每个参与活动且运行客户端的成员都需要上传自己的完整原始 CombatLog，不采用主客户端独占完整日志的模式。每份日志必须关联平台用户、设备、游戏角色 GUID、活动、录像和采集时间信息，云端分别保留来源后再进行汇总分析。角色 GUID 用于游戏内角色匹配，平台用户身份仍以登录会话和上传授权为准。

日志事件至少用于识别：

- 活动开始和结束
- 进入或离开战斗
- Boss 和难度
- Pull 开始和结束
- 是否击杀
- 参战角色
- 死亡
- 技能施放
- 伤害和治疗
- Buff 与 Debuff
- 打断和驱散

### 5.4 本地状态

每个上传单元必须具备稳定标识和状态，支持幂等重试。基础状态包括：

- 等待录制
- 录制中
- 等待上传
- 上传中
- 等待云端处理
- 已完成
- 可重试失败
- 不可恢复失败
- 已取消

客户端崩溃或设备重启后，未完成任务必须能够恢复。

## 6. 上传协议

### 6.1 上传方式

第一阶段不要求边录边传，默认采用 Pull 结束后上传：

- 客户端根据 CombatLog 识别 Pull 开始和结束，结束录制并关闭本场视频文件。
- 客户端截取并压缩本场对应的完整原始 CombatLog 区间。
- 客户端先提交 Pull、角色和文件元数据，再通过受控地址优先上传压缩日志，并行或随后上传视频。
- 视频可以按文件大小使用单次 PUT 或 S3 Multipart；Multipart 只承担断点续传，不作为播放分片。
- 上传完成后提交完整性清单，云端据此确认缺失、重复或损坏的文件。
- 断网时写入本地队列，恢复网络后继续上传。

Pull 结束后约 5 秒内，Web 端应能看到该 Pull 及其日志、视频上传和处理状态。视频只有在实际上传和必要处理完成后才能播放，第一阶段不承诺 Pull 结束后 5 秒内完整视频可播放。具体 Multipart Part 大小、并发数、带宽上限和重试退避由技术验证确定，不能散落为客户端魔法值。

### 6.2 可靠性要求

- 视频大文件使用可恢复的 Multipart Upload，日志和小文件使用可重试的独立对象上传。
- 每个上传对象携带稳定标识、内容校验值、开始时间和结束时间；Multipart 额外保存 upload ID、Part 编号和 ETag。
- 服务端接口必须幂等，重复提交不能产生重复视频或事件。
- 客户端只有在服务端确认持久化后才能标记上传对象或 Multipart Part 完成。
- 云端能识别缺失文件、缺失 Part、乱序、重复、损坏和超时未完成的上传。

### 6.3 数据存储原则

- PostgreSQL 保存用户、团队、活动、Pull、上传状态、事件索引和复盘标记等结构化数据。
- 视频、原始日志和转码产物保存到对象存储，不写入 PostgreSQL 大字段。
- 对象存储必须使用私有访问，Web 播放通过短期授权地址或受控代理访问。
- 原始文件、处理产物和数据库记录需要统一的删除与保留策略。

## 7. 云端处理

### 7.1 处理流水线

云端处理按以下阶段推进：

1. 接收并校验上传文件及 Multipart 完成状态。
2. 合并或登记 CombatLog 批次。
3. 解析活动、Boss、Pull、玩家和战斗事件。
4. 将不同客户端记录关联到同一团队活动和 Pull。
5. 计算视频时间、日志时间与统一 Pull 时间之间的偏移。
6. 检查视频完整性并生成播放所需产物。
7. 生成事件索引、死亡窗口和基础复盘数据。
8. 发布可查看的云端复盘。

各阶段必须独立记录状态和错误，支持安全重试，不能因单个团员的视频失败阻塞整个 Pull。

### 7.2 多客户端日志汇总

同一 Pull 下，不同成员上传的 CombatLog 会包含大量重复事件。云端不能简单拼接日志，而需要：

- 分别校验每份日志的批次连续性和完整性
- 为事件生成稳定指纹并识别重复事件
- 使用多份日志互相补充缺失区间
- 为保留的统一事件记录一个或多个来源日志
- 选择可信度更高的时间和字段，记录冲突与选择依据
- 生成一份面向复盘的统一事件流
- 保留每份成员日志与其录像之间的时间映射

任意一名成员日志缺失或损坏不能阻塞整个 Pull；系统应使用其他成员日志完成团队时间线，同时明确标记该成员录像的同步可信度。

### 7.3 核心数据层级

统一使用以下业务层级：

- 团队
- 团本活动
- Boss
- Pull
- 参战成员
- 成员录像
- 成员原始录像文件
- 播放视频片段
- 原始日志文件
- 战斗事件
- 时间同步结果
- 复盘标记

同一成员可能缺少录像但存在日志，也可能录像成功但日志不完整。数据模型和页面必须允许部分成功。

## 8. 时间同步

时间同步是产品核心能力，必须独立设计和验证。

### 8.1 时间基准

客户端同时记录：

- 日志事件携带的时间
- 原始录像文件的本地单调时钟区间
- 客户端当前绝对时间和时区信息
- 录制开始、暂停、恢复和结束时间
- 上传对象标识和 Multipart 状态

云端以 Pull 开始为统一时间零点，计算每个成员录像相对于该时间线的偏移。

### 8.2 同步校准

同步可以组合使用：

- CombatLog 中共同出现的战斗事件
- Boss 开战和击杀事件
- 客户端记录的录制边界
- 多名成员日志中的相同事件序列

必须保存同步方式、偏移量和可信度。可信度不足时页面应显示警告，并允许有权限用户手动微调偏移；不能静默展示明显错位的视频。

### 8.3 同步验收

第一阶段目标是在正常录制和日志完整的情况下，让同一事件在不同成员视角中的时间偏差满足可用的复盘要求。具体误差阈值需要通过真实团本样本确定后写入配置和验收标准。

## 9. Web 云端复盘

### 9.1 活动列表

活动列表展示：

- 团本和难度
- 活动开始与结束时间
- Boss 列表
- Pull 数量
- 击杀情况
- 参与人数
- 已上传录像人数
- 云端处理状态
- 数据保留期限

### 9.2 Pull 列表

每个 Pull 展示：

- Pull 编号
- Boss
- 战斗时长
- 是否击杀
- Boss 剩余血量，可解析时展示
- 死亡人数
- 首死玩家
- 可用录像数量
- 缺失或处理失败的录像数量
- 是否包含复盘标记

### 9.3 第一视角切换播放器

所有成功同步的成员录像都挂载到同一 Pull 时间线，但页面同一时间只播放一个成员视角。页面需要支持：

- 点击成员后切换到该成员的第一视角录像
- 切换视角时保持当前 Pull 时间、播放或暂停状态、倍速和音量
- 播放、暂停、跳转和倍速控制
- 播放当前视角的音轨
- 按角色名、职业、专精和职责筛选视角
- 显示录像缺失、上传中、处理失败和同步警告
- 从战斗事件跳转到对应时间点
- 当前视角没有覆盖目标时间时明确提示，并允许选择其他可用视角

云端需要将全部可用视角对齐到统一 Pull 时间线。第一阶段不实现多路并排播放，浏览器只加载当前视角；为了缩短切换等待，可以按需预取候选视角的播放清单，但不得预加载全团视频内容。

### 9.4 统一事件时间线

时间线至少包含：

- Boss 阶段
- Boss 关键技能
- 玩家死亡
- 玩家施法
- 主要伤害与治疗事件
- Buff 和 Debuff
- 打断和驱散
- 复盘标记

支持按事件类型、玩家和技能筛选。点击事件后，当前播放的第一视角跳转到对应统一时间点。

### 9.5 死亡复盘

每次死亡展示：

- 玩家和死亡时间
- 直接致死技能
- 死亡前生命值变化
- 死亡前受到的伤害和获得的治疗
- 当时的 Buff 与 Debuff
- 个人减伤、外部减伤和团队减伤事件
- 治疗石、治疗药水等日志中可确认的使用记录
- 死亡前默认 15 秒的事件窗口
- 一键打开死亡时间点的本人及相关成员录像

页面必须区分日志事实与系统推断，不能自动输出确定责任归属。

### 9.6 复盘标记

团长和分析员可以：

- 在统一时间线上添加标记
- 填写标题、说明和分类
- 关联玩家、技能或事件
- 标记重点片段
- 复制当前时间点的复盘链接
- 修改或删除自己有权限管理的标记

第一阶段不建设多人实时批注协作。

## 11. MVP 优先级

### 11.1 P0：技术闭环验证

必须先证明：

- Windows 客户端能稳定录制正确的魔兽世界画面。
- 客户端能增量读取 CombatLog，并识别一场 Boss Pull。
- Pull 结束后的视频和完整原始日志能可靠上传，视频 Multipart 能在中断后恢复。
- 云端能解析日志并生成统一 Pull 时间线。
- 单个成员的视频能与日志事件同步播放。
- 两个成员的视频能对齐到同一时间线并切换查看。
- 客户端或网络中断后，上传任务能够恢复且不重复数据。

P0 只需要内部技术页面，不要求完整视觉设计。

### 11.2 P1：小团队可用

- 用户、团队和简单权限
- 客户端录制配置、预览和状态诊断
- 活动与 Pull 自动关联
- 多成员上传和部分失败处理
- 活动列表和 Pull 列表
- 单播放器成员视角切换
- 统一事件时间线
- 死亡事件跳转视频
- 复盘标记和链接分享
- 数据保留和删除

### 11.3 P2：复盘增强

- 更丰富的 Boss 机制识别
- 死亡原因规则分析
- 团队问题累计统计
- WCL 报告关联或导入
- 排轴计划与实际执行对比
- 转码档位和自适应播放
- 更精细的客户端自动更新与诊断

## 12. 明确不做

第一阶段不实现：

- 公开直播和观众观看
- 多路视频并排或同时播放
- AI 自动判责
- AI 自动生成完整复盘结论
- 完整团本排轴编辑器
- STT 或 NSRT 导出
- 国际服和怀旧服
- macOS 客户端
- 移动端完整复盘
- 装备、出勤、招募、Loot Council 和 DKP
- 完整职业循环分析
- 自有 WoW 插件

## 13. 非功能要求

### 13.1 可靠性

- 客户端崩溃、游戏重启、断网和云端短暂不可用不能导致整场数据丢失。
- 上传、解析、关联和转码任务必须幂等并可重试。
- 单个成员失败不能阻塞其他成员的复盘发布。

### 13.2 性能

- Pull 结束并提交元数据后，目标是在约 5 秒内出现在活动处理状态中。
- Pull 结束后，已上传完成的视角应尽快进入可复盘状态。
- 视频可播放时间受文件大小、用户上行带宽和云端处理耗时影响，不承诺结束后 5 秒内可播放。
- Web 页面不能因为团队拥有大量视角而一次加载全部视频资源。

具体时延、并发、码率和容量指标需要根据 P0 实测结果确定。

### 13.3 安全与隐私

- 麦克风录制默认关闭，并明确提示录制状态。
- 视频和日志默认仅团队内授权用户可见。
- 上传和播放必须使用加密传输。
- 对象存储不得公开暴露永久地址。
- 用户需要知道录制内容、存储期限和删除方式。
- 删除活动时必须覆盖原始视频、转码产物、日志、事件索引和相关授权链接。

### 13.4 时间

- 业务展示时间统一使用 `Asia/Shanghai`。
- 视频同步计算必须保留原始时间、单调时钟和统一时间线之间的关系。
- 前端不得对后端已格式化的业务时间再次进行时区转换。

## 14. 第一阶段验收流程

1. 两名团员分别在 Windows 设备安装并登录客户端。
2. 两人加入同一个团队，并完成游戏、日志和录制检查。
3. 客户端预览确认采集窗口正确。
4. 两人进入同一场团本活动并开始一个 Boss Pull。
5. 客户端持续读取 CombatLog 和录制视频，在 Pull 结束后关闭本场文件并开始上传。
6. 其中一台设备短暂断网后恢复，未完成文件或 Multipart Part 继续上传。
7. Pull 结束后，云端识别两人的记录属于同一个 Pull。
8. 云端解析战斗事件，并完成两路视频与统一时间线的同步。
9. 团长在 Web 端打开该 Pull，看到两路视角及各自处理状态。
10. 团长播放一路视频，在相同时间位置切换到另一路视频。
11. 团长点击一条死亡或 Boss 技能事件，当前视角跳转到对应时间点；切换成员后仍保持该 Pull 时间。
12. 团长添加复盘标记并通过链接重新打开同一时间点。
13. 团长能识别缺失文件或播放片段、同步警告及处理失败，不会看到伪装成完整的数据。
14. 团长删除测试活动后，相关视频、日志和处理产物进入明确的删除流程。

## 15. 产品成功标准

第一阶段成功需要满足：

1. 普通团员能在一次配置后稳定完成录制和自动上传，不需要手工剪辑视频。
2. 同一 Pull 的多个成员录像可以在统一时间线上快速切换，且切换后保持当前复盘时间。
3. 团长能从关键战斗事件直接定位到相关成员当时的游戏画面。
4. 网络或客户端短暂失败不会导致整场记录不可恢复。
5. 缺失和低可信度数据会被明确展示，不产生错误的完整性预期。

## 16. 技术验证与未决决策

进入正式实现前必须完成以下验证：

- `aza547/wow-recorder` 的许可证、第三方依赖和可再分发边界。
- OBS 的嵌入、调用、插件或独立进程方案，以及对应许可证和升级维护成本。
- Windows 客户端框架选择。
- 中国区正式服 CombatLog 的开启方式、格式差异和版本变化。
- 游戏窗口采集在全屏、无边框和多显示器场景下的稳定性。
- 视频编码器、容器格式、分辨率、帧率、单场文件大小和 Multipart Part 大小。
- 对象存储、上传协议、转码方案和播放格式。
- 两人、十人和二十人团队的带宽、存储成本和处理吞吐。
- 第一视角切换耗时、时间保持精度和播放失败降级行为。
- 视频与日志同步误差的验收阈值。
- 原始视频、转码视频和日志的默认保留周期。
- Pull 结束后状态可见时延，以及不同码率和上行带宽下的视频可播放时延。
- 是否需要在后续阶段增加战斗中视频分片上传，以缩短 Pull 结束后的等待时间。

这些结论需要通过 P0 原型和真实团本样本验证后，写回本文件和项目配置，不得在业务代码中固化未经验证的假设。
