# 2026 年 9 月项目对话记录

## 2026-09-06：本地 Boss 自动录像闭环

- 用户目标：先实现 OBS 持续录像与 CombatLog 战斗起止结合，Boss 开战前保留 5 秒，结束后自动得到本地视频；暂不实现技能 Tooltip、云端上传和多人同步，不使用 SQLite。
- 关键讨论：参考 Warcraft Recorder 的持续缓冲与日志触发思路，但沿用项目现有 OBS WebSocket 路线；CombatLog 不负责启停 OBS，只定义 Pull 和裁切时间窗口。
- 决定：采用 OBS 高级输出手动文件分割，结束后保留 10 秒尾帧；Rust 用版本化 JSON 保存日志游标、Pull 状态和源文件时间映射；固定 LGPL FFmpeg 随包分发并用 stream copy 生成 MP4 与 manifest。
- 处理结果：完成 CombatLog 目录发现、增量读取、当前/旧日期解析和 Pull 状态机；完成 OBS 持续录像、无中断轮转、源锚点、原子索引、FFmpeg 裁切及严格解码校验；设置页接入真实 CombatLog 状态，直播不再停止持续录像。
- 验证：`cargo test --lib` 35 项全部通过；`npm run build` 成功，仅有大 chunk 警告；真实 WoW/OBS 联调识别多场 Boss，其中“达萨大王”完成尾帧、分割、成片、manifest 和严格解码退出码 0。该场跨开发热重载，因此按缺片录像标记为 `partial`，不作为完整时间轴样本。
- 未决事项：回放页尚未接入本地录像列表；技能时间轴与 Tooltip、云上传和多人同步留待后续；需在稳定 release 环境连续验证至少 3 场 Boss，并补充失败任务重试入口；精准时间轴前需实测 stream-copy 关键帧落点并加入墙钟/单调时钟双锚点。

## 2026-09-09：本地 HLS 回放接入

- 用户目标：在现有本地 Boss 自动录像基础上完成前端回放，先不实现技能标签、云端上传和多人同步，并确认 hls.js 与 Media Chrome 的职责边界。
- 关键讨论：hls.js 负责读取 HLS 清单和分片并挂载到原生 `video`，Media Chrome 只负责播放、进度、音量、倍速和全屏控件；两者不是互斥替代关系。OBS 仍持续录制，CombatLog 只定义每场 Boss 的前后各 5 秒成片边界。
- 决定：保留最终 MP4 作为正式本地及后续上传资产，同时使用内置 FFmpeg stream copy 生成 CMAF/fMP4 HLS；通过受限 Tauri 自定义协议提供固定 Pull 目录内的播放文件，前端轮询 Rust 本地录像索引。
- 处理结果：新增 HLS 生成、旧 MP4 自动补齐和受限本地协议；回放页移除 fixture，接入真实录像选择、状态、错误、HLS 播放与开战/结束时间轴跳转；固定使用 hls.js 1.7.2，继续使用 Media Chrome 控件。静态代码审查后补充了新 Pull 优先级、补处理重启恢复、HLS 失败保留 MP4 索引、轮询竞态和缺片时间轴保护。
- 验证：确认 `npm view hls.js` 当前版本与许可证后安装固定版本；`cargo test --lib` 共 37 项全部通过；`npm run build` 成功，仅有既有的大 chunk 警告；`git diff --check` 退出码为 0。已通过 `npm run tauri dev` 启动桌面客户端，并确认 Tauri 窗口、Vite 1420 监听和受管 OBS 进程正常存活。
- 未决事项：需在桌面客户端验证旧录像补齐、新 Pull 生成、HLS 播放和时间轴跳转；技能事件与 Tooltip、云端上传和多人同步留待后续；精准时间轴仍需实测关键帧落点和双时钟锚点。

## 2026-09-09：真实战斗时间轴与单 Pull 录像目录

- 用户目标：结合现有 OBS 持续录像和本地回放，用 CombatLog 自动生成开战前 5 秒、结束后 5 秒的 Boss 视频；每场使用独立文件夹和 JSON，回放轴从 0 到战斗结束，显示真实 Boss/个人技能及悬停说明，不保留假数据。
- 关键讨论：Boss 时间轴不能手写技能表，应从当前 Pull 对应的 CombatLog 字节区间提取；本地日志可提供 Encounter、时间、角色 GUID 和施法事件，但不能伪造 Archon/WCL 的 actorId、reportCode、fightId、评分和完整职业专精。
- 决定：继续使用 OBS 持续录像和结束后 5 秒 `SplitRecordFile`，不因单场战斗停止编码器；每个 Pull 保存 `video.mp4`、`metadata.json`、`combat-log.json` 与 `hls/`。本地时间轴以 `ENCOUNTER_START` 为 0，视频通过 `videoZeroMs` 增加 5 秒偏移。
- 处理结果：Rust 新增真实施法事件与玩家解析、Archon 风格本地元数据、旧产物目录迁移和启动时索引修复；React 显示真实人物名及 Boss/个人双轨时间轴，技能标记可悬停和点击跳转。修复 `COMBATANT_INFO` 非标准字段被误识别为玩家名的问题。
- 验证：`cargo test --lib` 40 项全部通过；`npm run build` 成功，仅有现存的大 chunk 警告；真实两场 Boss 均为 `ready`，前后各 5000ms，分别解析 27/29 个技能事件，MP4、HLS、metadata 与 combat-log JSON 均存在，旧错误玩家名已自动修复。
- 未决事项：本地第一版尚未索引死亡、Buff/Debuff、打断、驱散和技能图标；关键帧实际裁切偏差、连续多场和断线恢复仍需 release 环境验证；云端上传、WCL/Archon 增强和多人同步未开始。

## 2026-09-09：录像目录与视频可读命名

- 用户目标：录像文件夹和视频文件均按“时间-Boss 名称-难度-人物”命名。
- 关键讨论：磁盘名称需要可读，但本地 HLS 协议仍可使用内部 Pull ID，服务端再从录像索引解析真实目录，避免把中文路径编码规则扩散到前端。
- 决定：开战时间按 `Asia/Shanghai` 格式化为 `YYYY-MM-DD HH-mm-ss`，目录和 MP4 使用相同基础名称；Windows 非法字符替换为下划线。
- 处理结果：新录像直接使用可读名称，历史录像在客户端启动时自动迁移，索引路径、HLS 路径和 `metadata.json.key` 同步更新。
- 验证：`cargo test --lib` 42 项全部通过；两场现有真实录像均完成迁移，目录、MP4 和 metadata key 一致，视频与 HLS 文件存在。
- 未决事项：同一秒内出现完全相同 Boss、难度和人物的重复 Pull 时存在命名冲突可能，正常 CombatLog 流程下概率很低；若未来导入重复历史日志，需要增加明确的冲突命名规则。
